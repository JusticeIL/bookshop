ONLINE BOOKSHOP - ARCHITECTURAL PROPOSITIONS
============================================
(Home assignment - decisions and their rationale)

1. OVERALL SHAPE
----------------
A REST API web application: a single-page React client talks to a stateless
RESTful HTTP/JSON API (resource-oriented URLs, HTTP verbs carrying the
semantics, standard status codes), which owns the data. Three cleanly
separated tiers, deployed independently, plus a cache:

  React + TypeScript SPA  --HTTPS/JSON-->  Spring Boot 3 REST API  --JDBC-->  PostgreSQL 16
        (Vercel)                              (Render, Docker)                  (Neon)
                                                     |
                                                     +--RESP--> Redis (catalog read-cache)

The frontend never talks to the database; the backend is the single owner of all
business rules; the database schema is owned by versioned Flyway migrations, not
by the ORM (Hibernate runs in validate-only mode). Each tier can be replaced or
scaled without touching the others.

2. BACKEND - JAVA 21 / SPRING BOOT 3 REST API (MVC)
---------------------------------------------------
The backend is a REST API implementing the MVC pattern, built on Spring Web
MVC (the framework's name is literal):

  MODEL       JPA entities + Spring Data repositories (state) and the service
              layer (business rules) - the "M" is everything that knows and
              changes domain state.
  VIEW        The representation returned to the client: JSON rendered from
              DTO records. In a SPA architecture the React frontend is the
              rendered view; the API's JSON is the view model feeding it.
              (The single server-rendered HTML page is the authorization
              server's sign-in form, which OAuth2 requires - see section 3.)
  CONTROLLER  @RestController classes - thin HTTP adapters doing binding,
              validation and status codes only, delegating everything to
              services.

RESTful conventions: resources are nouns (/api/books, /api/cart/items/{id},
/api/orders/{id}); the verb carries the intent (GET read, POST create, PUT
replace, DELETE remove - cancelling an order is DELETE on the order resource);
responses use standard status codes (200, 201 on create, 400 validation, 401
unauthenticated, 404, 409) with a uniform JSON error envelope. The API is
stateless - every request carries its own bearer token, nothing is held in a
server-side session - which is what lets the backend scale horizontally.

Inside each feature package the layering is Controller -> Service -> Repository:

  * Controllers are thin: HTTP concerns only (binding, validation, status codes).
  * Services own transactions and business rules (stock checks, checkout
    atomicity), written in a functional style (streams, Optional chains).
  * Repositories are Spring Data JPA interfaces; no hand-written SQL in Java code.
  * DTOs are Java records - the API contract never leaks JPA entities, so the
    schema can evolve without breaking clients.

Caching: Redis fronts the hot catalog reads (paginated list 60s TTL, single
book 5min TTL) via Spring's cache abstraction - typed JSON serializers per
cache, and every stock-changing operation (checkout, cancellation) evicts both
caches so shoppers never see stale availability. A custom CacheErrorHandler
degrades gracefully: if Redis is down or not provisioned, requests are served
straight from PostgreSQL instead of failing.

Why Java/Spring here: strong compile-time typing, a mature security ecosystem,
first-class Postgres/Redis support, and WORA - identical jar locally and in the
Render container.

3. AUTHENTICATION - SELF-HOSTED OAUTH2 (AUTHORIZATION CODE + PKCE)
------------------------------------------------------------------
Authentication is real OAuth2, run entirely in-house: the backend embeds
Spring Authorization Server (Apache 2.0, no third-party or paid identity
provider, no external service to sign up for). The same Spring Boot process
therefore plays three roles:

  AUTHORIZATION SERVER  issues tokens at the standard endpoints
                        /oauth2/authorize, /oauth2/token, /oauth2/jwks and
                        /.well-known/oauth-authorization-server
  RESOURCE SERVER       the REST API validates the bearer tokens it receives
  CLIENT-FACING APP     serves the one sign-in page the flow needs

SIGN-IN HAPPENS IN THE APPLICATION'S OWN UI. The React login form posts the
credentials to POST /api/auth/login over TLS, and the response carries the
tokens:

  1. The SPA posts {email, password} to /api/auth/login.
  2. The backend verifies the BCrypt hash and mints an RS256 access token
     (24 h) plus a rotating refresh token (7 days) - the SAME tokens the
     authorization server issues, signed with the same key, registered in the
     same authorization store (see TokenIssuer).
  3. Every REST call carries "Authorization: Bearer <access token>"; the
     resource server verifies the signature against the published JWK set.
  4. On a 401 the SPA silently rotates its refresh token at
     POST /api/auth/refresh and replays the request once. Renewal lives on
     the API rather than /oauth2/token because that endpoint's refresh grant
     requires client authentication, which a browser client cannot provide.

This is the "first-party trusted client" pattern: the shop and the identity
store are the same product, owned by the same team, so there is no third party
to delegate to and the redirect dance would only add friction. The full
Authorization Code + PKCE endpoints remain live and standards-compliant for
any client that IS separate from us - the machinery is not bypassed, it is
shared.

Deliberate decisions:
  * The SPA is registered as a PUBLIC client: no client secret (a browser
    cannot keep one); when the authorization-code endpoint is used, PKCE is
    mandatory, which is what defends the code against interception.
  * Refresh tokens ROTATE on every use (reuseRefreshTokens = false); a replayed
    refresh token is rejected. Concurrent 401s coalesce into one renewal.
  * Tokens carry a "uid" claim, so the API resolves the caller from the token
    with no database round-trip per request - and never from client input.
  * Credential endpoints are rate limited to 10 requests per IP per minute.
  * A wrong password and an unknown email are indistinguishable in both message
    and response time (the password is checked against a dummy hash when no
    account matches), so the API cannot be used to enumerate customers.
  * The signing key is an RSA keypair generated at startup and never committed
    or persisted. Consequence, stated plainly: a backend restart invalidates
    outstanding tokens and users sign in again. For a shop of this size that
    is a fair trade against storing private key material.
  * Passwords are BCrypt-hashed; a wrong password and an unknown email produce
    the same message (no account enumeration).
  * Full names are validated at registration (two words, letters only in any
    alphabet, separated by exactly one space - enforced by @Pattern on the DTO
    and mirrored in the SPA) and reused as the shipping recipient at checkout,
    so the checkout flow never re-asks for the name.
  * Two security filter chains, each with the right posture: /api/** is
    stateless and header-authenticated, so CSRF protection is off (there is no
    cookie to forge with); the authorization endpoint's sign-in page is
    session-backed with CSRF on.
  * The users table keeps multi-provider identity columns (auth_provider,
    provider_id) as forward-compatible schema design; accounts are local.

Injection, XSS, CSRF, IDOR, clickjacking, enumeration, brute force and
information disclosure are addressed explicitly - SECURITY.md documents each
defence and where it lives in the code. In short: no SQL is ever assembled
from strings (every query is parameter-bound, and the one input that cannot be
bound - the sort column - is allow-listed); React escapes all output and a
strict CSP is sent on every response; bearer tokens leave no CSRF surface;
every user-scoped query filters by the token's uid, so one customer cannot
reach another's cart or orders.

4. DATABASE DESIGN - POSTGRESQL
-------------------------------
Relational engine chosen because the domain is inherently relational (users,
books, carts, orders with line items) and correctness at checkout needs ACID.

  users        id, email (UNIQUE), display_name, password_hash,
               auth_provider, provider_id, created_at

               EMAIL IS THE LOGIN IDENTITY. Every user has exactly one email
               and exactly one password, and the email is what they sign in
               with - so email carries a UNIQUE constraint at the database
               level (not merely a service-layer check). Consequences:
                 - registration rejects an already-registered email;
                 - a lookup by email always resolves to at most one row, which
                   is what makes "find user, then verify password hash" a
                   correct and unambiguous authentication step;
                 - the surrogate key (id) remains the stable foreign-key
                   target, so a user could change their email later without
                   breaking their carts and orders;
                 - lookups are case-insensitive and emails are normalised to
                   lower case on registration, so "Gal@x.com" and "gal@x.com"
                   cannot become two accounts.
               display_name holds the validated full name (two words, letters
               only) and is reused as the shipping recipient at checkout.
  books        id, title, author, pages, image_url (NULLABLE by requirement),
               price NUMERIC(10,2), stock, created_at
  cart_items   one row per (user, book) - UNIQUE constraint; quantity > 0 CHECK.
               The active cart lives server-side, so it survives devices/sessions.
  orders       user_id, status CHECK IN (CONFIRMED/SHIPPED/CANCELLED),
               total_amount, shipping fields, payment_reference (mock),
               created_at. Confirmed orders are cancellable for 24h after
               purchase: stock is restored and the row flips to CANCELLED
               (history preserved rather than deleted).
  order_items  IMMUTABLE SNAPSHOT of title + unit_price + quantity at purchase
               time - later catalog price edits can never rewrite order history.

Money is NUMERIC(10,2), never floats. All constraints (CHECKs, UNIQUEs, FKs) are
in the database, not only in application code: the DB is the last line of defense.

STOCK SAFETY (no overselling, three layers):
  1. UI      - a book with stock = 0 renders an "OUT OF STOCK" badge with the
               add-to-cart button disabled; the button also disables once the
               quantity already in the cart reaches available stock.
  2. Service - every add-to-cart and quantity change validates against current
               stock and returns a 400 with the exact remaining count.
  3. Database- checkout re-reads each book with SELECT ... FOR UPDATE
               (@Lock(PESSIMISTIC_WRITE)) inside the transaction, so two
               shoppers buying the last copy simultaneously serialize on the
               row: the first wins, the second is rejected. A CHECK (stock >= 0)
               constraint makes a negative stock physically impossible even if
               application logic were bypassed.
Checkout is a single transaction: lock rows -> validate stock -> decrement ->
snapshot prices -> create order -> empty cart; a failure anywhere rolls
everything back. Cancellation restores stock under the same row locks.

5. FRONTEND - REACT 18 + TYPESCRIPT 5.6 (VITE, ZUSTAND)
-------------------------------------------------------
  * Vite for instant dev feedback and a tiny static production bundle.
  * The TypeScript API layer mirrors the backend DTOs 1:1 - a contract change
    is a compile error, not a runtime surprise.
  * The OAuth2 client is hand-written against the Web Crypto API (~140 lines,
    no auth library): PKCE verifier/challenge generation, the authorization
    redirect, the code-for-token exchange and transparent refresh-token
    rotation on a 401.
  * Zustand for the two genuinely global slices (auth session, cart). It avoids
    Context re-render cascades with ~zero boilerplate; component-local state
    stays in useState where it belongs.
  * Cart operations are OPTIMISTIC: the UI updates instantly and rolls back to
    the previous server state if the API rejects (e.g. out of stock), showing
    the server's error message.
  * Route guards send unauthenticated users into the OAuth2 flow and return
    them to where they were once tokens are in hand.
  * Feedback is delivered through a toast system: green = success, red = error
    (including "server unreachable", throttled so bursts cannot spam), orange =
    everything else (info, warnings, sign-out).
  * Presentation: a "liquid glass" theme (translucent blurred surfaces, pill
    controls, custom-rendered selects) with an iOS-style light/dark switch in
    the navbar; the choice is persisted and defaults to the OS preference.
    Completing an order fires a dependency-free canvas confetti celebration
    with an animated rainbow heading.

6. DEPLOYMENT - 100% FREE, STABLE FOR THE REVIEW WEEK
-----------------------------------------------------
  Frontend  Vercel        static CDN, zero cold starts, free SSL, git-push deploys.
  Backend   Render free   Docker web service; multi-stage build -> slim JRE image;
                          /api/health as health check.
  Database  Neon free     serverless Postgres, no 30-day expiry (Render's free
                          Postgres expires after 30 days - avoided on purpose),
                          TLS required, generous free storage for this scale.
  Cache     Redis         local: a redis:7-alpine container in docker compose.
                          Hosted: any free Redis-compatible endpoint (e.g.
                          Upstash) via REDIS_URL. OPTIONAL BY DESIGN - if
                          REDIS_URL is absent or the server is unreachable, the
                          cache layer logs a warning and every request falls
                          through to PostgreSQL, so the deployment never depends
                          on it being up.

Cold-start mitigation: Render free instances sleep after ~15 min idle (first hit
then takes ~50 s). A GitHub Actions cron pings /api/health every 10 minutes so
reviewers always land on a warm service. Neon's scale-to-zero adds only ~1 s and
needs no mitigation. Expected load (<100 concurrent visitors) is far below the
free-tier ceilings of all three services.
